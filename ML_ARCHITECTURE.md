# ML Architecture — AI Symptom Checker

This document explains how machine learning is used in MediVerse AI:
what algorithm was chosen and why, the full training pipeline, how
predictions are served in production, and the honest limitations of
the approach. Intended as a reference for the project report and viva.

---

## 1. Where ML lives in the codebase
ml/ Training pipeline (offline, run once)
├── data/ Raw dataset (4,920 records, 41 diseases, 131 symptoms)
├── download_data.py Fetches the dataset from its public source
├── train_model.py The core training script
└── notebooks/disease_prediction_model.ipynb EDA + training + evaluation, fully documented

backend/app/ai/ Production inference (online, runs per-request)
├── model/ Trained artifacts (generated by ml/train_model.py)
│ ├── disease_model.joblib The serialized trained classifier
│ ├── symptom_list.json Feature ordering (131 symptom names, fixed order)
│ └── disease_metadata.json Per-disease precautions/risk levels
├── ml_predictor.py Loads the model, runs inference
└── symptom_checker.py Rule-based fallback (NOT ML - keyword matching)

backend/app/services/prediction_service.py Orchestrates: ML model -> fallback -> persistence
backend/app/models/prediction.py DB table storing every prediction made

Training and inference are two completely separate code paths. The
model is trained once, offline, using `ml/train_model.py`. The trained
artifacts are then copied into the backend and loaded once at server
startup - the backend never re-trains anything.

## 2. The algorithm: Decision Tree Classifier

**Library:** `sklearn.tree.DecisionTreeClassifier`
**Task type:** Supervised multi-class classification (1 of 41 disease labels)

### How it works internally

A decision tree builds a flowchart of binary questions. At each node
during training, the algorithm evaluates every one of the 131 symptom
features and asks: *"if I split the data on 'does the patient have
symptom X?', which split makes the resulting groups most pure (i.e.
dominated by a single disease)?"*

The splitting criterion (scikit-learn's default) is **Gini impurity**:
Gini(node) = 1 - Σ(pᵢ)²
where `pᵢ` is the proportion of samples belonging to disease class `i`
at that node. A Gini of `0` means the node is perfectly pure (only one
disease present). The algorithm greedily picks the split that
minimizes weighted Gini impurity across the resulting child nodes,
then recurses on each child. This is the **CART algorithm**
(Classification and Regression Trees).

Splitting continues until every leaf is pure or a stopping condition
is met. This project deliberately does **not** cap `max_depth`: with
41 classes sharing only ~304 unique symptom patterns in the dataset, a
shallow tree cannot create a pure leaf for every disease. This was
verified empirically - capping depth at 15 dropped test accuracy to
~40%; removing the cap reached a tree depth of 60 with pure leaves and
100% test accuracy.

### Why this algorithm (justification for the report/viva)

- **Interpretable** - the trained tree is literally a sequence of "does
  the patient have symptom X?" questions, which maps directly onto how
  a clinician reasons through a symptom checklist.
- **No feature scaling required** - all features are binary (0/1),
  which decision trees handle natively without normalization.
- **Fast** - trains in well under a second on 4,920 x 131 data, no GPU
  required, appropriate given project scope and hardware constraints.
- **Appropriate baseline** - simple and explainable before considering
  heavier approaches (ensembles, neural networks) that this project's
  scope did not require.

## 3. The training pipeline (`ml/train_model.py`)

| Step | What happens | Function |
|---|---|---|
| 1. Load | Parse `dataset.csv` (`Disease, symptom_1, symptom_2, ...`, variable-length rows), strip inconsistent whitespace | `load_raw_rows()` |
| 2. Feature engineering | **One-hot encode**: build a 131-column binary feature matrix, one column per unique symptom, `1` if present in that row | `build_dataset()` |
| 3. Split | 80/20 train/test split, **stratified** by disease label so every class is proportionally represented in both sets | `main()` |
| 4. Train | Fit `DecisionTreeClassifier(random_state=42)` on the training set | `main()` |
| 5. Evaluate | Test-set accuracy, 5-fold cross-validation, full classification report (precision/recall/F1 per class) | `main()` |
| 6. Persist | Save the fitted model with `joblib.dump()`; save the ordered symptom list as JSON (inference must build feature vectors in this exact column order); merge disease descriptions/precautions/severity into `disease_metadata.json` | `main()` |

### Results

- **Test accuracy: 100%**
- **5-fold cross-validation accuracy: 100%**

### Why accuracy is 100% - and why that's expected, not a red flag

The dataset is a clean, educational one where each disease maps to a
small, fixed set of exact symptom combinations - only ~304 unique
(disease, symptom-set) patterns across 4,920 rows (verified via EDA,
see the notebook). Because the same exact patterns repeat across the
train/test split, the tree can memorize the mapping perfectly and
reproduce it exactly on held-out data.

This is a documented property of this specific dataset - **not** a
claim that the model would be 100% accurate on messy, real-world
symptom reporting. A production clinical system would need a larger,
noisier, real dataset, probabilistic symptom weighting, and likely a
probabilistic model rather than a single deterministic decision path.
This is precisely why the platform also keeps a rule-based fallback
engine as a defensible safety net (see Section 5).

### Feature importance

`model.feature_importances_` gives a Gini-based score per symptom,
showing which symptoms the tree relies on most across its splits.
Printed in Section 8 of the notebook. This demonstrates the model
found meaningful, non-arbitrary signal in the data rather than
memorizing labels randomly.

## 4. Model persistence

Three artifacts are produced by training and loaded by the backend:

| File | Contents | Purpose |
|---|---|---|
| `disease_model.joblib` | The serialized `DecisionTreeClassifier` object | The trained model itself |
| `symptom_list.json` | Ordered list of 131 symptom names | Defines feature vector column order - must match exactly between training and inference |
| `disease_metadata.json` | Per-disease description, precautions, derived risk level | Enriches predictions with human-readable advice |

`joblib` is used instead of raw `pickle` because it's more efficient
for objects containing large NumPy arrays (which scikit-learn models
are built on).

|
v

so the UI can display a "Trained ML model" vs "Rule-based fallback"
badge for transparency

### Model loading strategy

The model is loaded **once**, at FastAPI process startup, via a
module-level `joblib.load()` call in `ml_predictor.py` - not
re-loaded on every request. This is standard ML-serving practice:
deserializing a model per-request would be wasteful; the same
in-memory model object is reused across all requests for the life of
the process.

### Where confidence scores come from

`predict_proba()` for a Decision Tree does not compute an abstract
uncertainty estimate - it returns the class distribution of *training*
samples that landed in the same leaf node as the input. If a leaf is
100% pure (only one disease's training samples ever reached it - true
for most leaves in this tree, given the 100% training/test accuracy),
the reported probability for that class is exactly `1.0`, because no
other class is represented in that leaf at all. This is a mechanically
grounded number, not an inflated or arbitrary confidence figure.

## 6. What's explicitly NOT machine learning in this project

For precision when discussing the project:

- **The rule-based fallback engine** (`symptom_checker.py`) - simple
  keyword-overlap scoring, no learned parameters, no training data.
- **Symptom input is a fixed checklist**, not free text - there is
  **no NLP** anywhere in this pipeline.
- **No neural networks / deep learning.**
- **No hyperparameter tuning** (e.g. `GridSearchCV`) - a deliberate
  scope decision given project constraints, documented rather than
  hidden.

## 7. Honest limitations (for the report)

1. The dataset is synthetic/templated, not real clinical data -
   accuracy here should not be read as "the model would be 100%
   accurate on real patients."
2. A Decision Tree gives a single deterministic prediction path; it
   doesn't model uncertainty between co-occurring conditions the way a
   probabilistic model (e.g. Naive Bayes, or a calibrated classifier)
   would.
3. Real-world symptom reporting is noisy, partial, and often free-text
   rather than a clean checklist - a production system would need
   NLP-based symptom extraction ahead of this classifier.
4. The model was intentionally kept simple (no hyperparameter search,
   no ensembling) given project scope and hardware constraints - a
   documented scope decision, not an oversight.
